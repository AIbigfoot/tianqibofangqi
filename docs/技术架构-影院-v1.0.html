影院（Cinema）技术架构方案 — 桌面客户端、可替换内核、可迭代边界

本文档落地 PRD v1.1 的 FR-07「架构上能够支持持续迭代」：给出技术选型、分层与依赖方向、扩展点契约、关键链路与数据迁移策略。 产品行为以 PRD 为准，本文档不重新定义需求。

01架构目标与硬约束

以下 6 条是本文档所有选型与结构决策的判据。若某方案与其中任一条冲突，则被否决，理由必须写在本文档对应位置。

编号约束来源与含义对结构的强制要求
C1本地优先、离线可用FR-01 需扫描本机目录，FR-05 需尽量不把音频送出本机核心能力（入库、检索、播放）不得依赖常驻网络服务；网络能力必须可关闭且失败可降级
C2可替换内核FR-07「字幕能力可替换」「元数据来源可切换」领域层只依赖端口（trait/接口），具体实现注册在适配器层，替换实现不改动领域与应用代码
C3多路并行播放FR-06 同时播放 2–6 路，且各路互不影响播放实例必须可多实例化且故障隔离：单路崩溃不得影响其他路与主界面
C4重负载隔离FR-05 实时字幕在播放中持续占用算力识别/翻译必须与 UI、播放解耦到独立承载单元，可挂起、可限流、可崩溃重启
C5数据不丢失FR-07「用户数据可导出与导入，升级后不丢失」数据存储需带 schema 版本；结构变更只能前进式迁移，且迁移前自动备份
C6增量演进FR-07「新增源类型/标签维度不改动既有行为」数据模型面向「条目 + 维度标签」而不是固定字段枚举；新功能以默认关闭的功能开关发布

02技术选型

选型原则：每个关键位置给出被选方案、被否决方案与被否决原因，避免后续迭代时反复推翻决策。

客户端外壳与语言

方案结论理由 / 否决原因
Tauri 2 + Rust 核心 采用 直接命中 C1–C5：Rust 侧可零拷贝调用 libmpv 与 ASR 原生库、可以进程方式隔离重负载（C4）、安装体积小、无需把 Node 运行时打进客户端。前端沿用 Web 技术栈，海报墙这类界面开发效率不受影响。
Electron + Node 核心 备选 生态与招人成本更低，但需同时维护 Node 与 WebView 两层运行时；ASR/解码等重负载若留在 Node 侧难以精细限流（弱 C4），体积与内存开销更大。仅当 Tauri 侧 GPU 渲染验证失败时切换（见风险 R1）。
纯 Web 应用（浏览器内） 否决 无法稳定扫描任意本地目录（C1 不满足），也无法承载多路本地解码与识别负载（C3/C4 不满足）。

播放内核

方案结论理由 / 否决原因
libmpv（嵌入式） 采用 一个内核同时覆盖：多实例并发解码、硬件加速、HDR、音轨/字幕轨切换、字幕样式与时间轴偏移（FR-04 全部控制项）、音频直通。多实例是最省成本地实现 FR-06 的路径。
HTML5 video 元素 否决 编解码受 WebView 限制，MKV/HEVC/多音轨支持不一致；无法在同一进程稳定驱动多路并发（C3 不满足）。
ffmpeg + 自研渲染管线 否决 需要自行实现音视频同步、硬件色彩管理、字幕渲染与 seek 策略，首版成本远超收益，且这些正是 mpv 已成熟的部分。

实时字幕（ASR + 翻译）

方案结论理由 / 否决原因
本地推理（faster-whisper 或 whisper.cpp） 默认 满足 C1（可离线）与隐私承诺（音频不出本机）；无按量成本。代价：首次需下载模型、CPU 模式延迟较高，需按 FR-05 提供资源上限与降级。
云端 ASR / 翻译 API 可选开关 延迟与多语种覆盖更好，但引入费用与隐私边界。作为用户显式授权的可选实现接入同一端口（SubtitleEngine），不改变上层代码；默认关闭。
仅外挂字幕匹配 否决 正是 PRD 要解决的问题（找不到匹配字幕），无法作为方案主体。

其余组件

位置选型理由
前端框架React + TypeScript + Vite海报墙与多屏这类状态密集界面需要成熟生态；TS 类型与 Rust 侧生成的类型声明可共享（见 a4 契约生成）
前端状态Zustand（视图状态） + 查询层缓存（库数据）库数据以只读查询为主，适合缓存 + 失效；播放态属高频本地状态，放轻量 store
本地存储SQLite + FTS5，WAL 模式单文件、事务可靠、FTS5 直接支撑 FR-03 的搜索；条目量级（万级）远未到需要独立数据库服务的程度
媒体与元数据获取HTTP 客户端 + 可插拔元数据提供者（默认 TMDB 类服务）FR-07 要求来源可切换、可新增、可关闭
并发模型Rust：tokio 异步任务处理 IO；ASR 独立子进程；播放由 libmpv 自带线程满足 C4：识别崩溃或卡死时可单独重启，UI 与播放不受影响
打包与更新Windows：MSI/NSIS 安装包 + 签名 + 更新通道（稳定/尝鲜）FR-07 要求升级后数据不丢失，因此更新必须与数据迁移绑定发布
取舍说明（供评审） Tauri 的决定性依据是 libmpv 与 ASR 原生库都在本地进程边界内可控。若评审更看重团队既有技术栈与交付速度，Electron 仍可在不改动本文档 a3/a4 结构的前提下替换 —— 因为所有本地能力都被封在端口之后，替换外壳只影响适配器层实现。

03分层与依赖方向

依赖只能指向内侧。外层的每一次替换（换外壳、换内核、换元数据源、换 ASR 引擎）都只影响最外层的一格。

禁止事项（评审与 CI 均可检查）

  • L2 不得出现 sqlite、http、mpv、whisper 等任何具体技术名词与 IO 调用。
  • L0 不得直接调用 L3/L4；前端只能通过 L1 暴露的命令与服务访问本地能力。
  • L3 不得互相直接调用（例如元数据提供者不得直接操作播放器），跨能力协作一律经 L1 编排。
  • 新增一个媒体源类型、一个元数据源、一个字幕引擎，都必须是「新增一个 L3 实现 + 在注册表登记」，不允许修改 L2。

04端口与扩展点契约

下面 5 个端口对应 PRD FR-07 的 7 个可扩展点。契约以 Rust trait 定义在 L2，实现放 L3；前端可见的类型通过代码生成同步到 TS。

P-01MediaSourceProvider — 媒体源类型

// L2 声明；L3 实现：LocalFolderProvider / LanPathProvider / DirectUrlProvider / (后续) CloudDriveProvider
trait MediaSourceProvider {
  fn kind(&self) -> SourceKind;
  // 枚举候选项：只做「发现」，不做解析与入库
  fn discover(&self, src: &MediaSource, sink: &dyn DiscoverSink) -> Result<DiscoverStat>;
  // 打开播放句柄：本地返回路径，在线返回可播放地址（必要时带请求头）
  fn open(&self, item: &MediaItem) -> Result<PlayableRef>;
  fn probe(&self, ref_: &PlayableRef) -> Result<StreamFacts>; // 时长/分辨率/音轨/内嵌字幕清单
}
约束说明
增量与幂等discover 必须可被重复调用：已存在条目按稳定键（源 + 相对路径 / 规范化 URL）合并，不重复入库，不覆盖用户数据（PRD FR-01）
可取消DiscoverSink 支持取消信号，取消后已提交条目保留（PRD FR-01 异常表）
失败隔离某源实现抛错只置该源为「扫描失败」，不影响其他源与其他条目

P-02MetadataProvider — 元数据与海报来源

trait MetadataProvider {
  fn name(&self) -> &str;
  fn priority(&self) -> u8;                       // 多提供者并存时的顺序
  fn candidates(&self, hint: &ParseHint) -> Result<Vec<MetadataCandidate>>;
  fn fetch(&self, id: &ProviderRef) -> Result<Metadata>; // 含封面候选与简介
}
  • 可关闭：全部提供者被关闭时，入库仍必须成功，条目落为「元数据待补全」并使用占位海报（PRD FR-01/FR-02）。
  • 不覆盖用户数据：任何提供者写入都必须经 FieldLock 过滤：用户编辑过的标题/海报/标签为锁定字段，写入被跳过（PRD 「用户已锁定」）。
  • 失败不阻塞：抓取为异步补齐流程，条目先可用后补齐；重试次数与退避在 L1 统一控制，不在提供者内实现。

P-03SubtitleEngine — 识别与翻译

trait SubtitleEngine {
  fn id(&self) -> &str;
  fn locality(&self) -> EngineLocality;        // Local | Remote —— 供 UI 显式告知隐私（PRD FR-05）
  fn languages(&self) -> (LangSet, LangSet);     // 支持的原声集 / 目标语集
  fn start(&self, cfg: SessionCfg, audio: AudioTap) -> Result<SessionHandle>;
  // 音频进入 start 返回的 sink；结果以事件流出口：Partial(原文) → Final(原文) → Translated(译文)
}
enum CueEvent { Partial{text,conf}, Final{cue}, Translated{cue}, Quality{level}, Failed{reason} }
约束说明
统一产物无论本地还是云端引擎，结果统一为 SubtitleTrack 对象（PRD 核心对象），因此播放器与「保存为字幕轨道」功能对引擎来源无感
可中断SessionHandle 必须支持 pause/resume/seek_reset/stop，与播放状态联动（PRD FR-05「拖动进度条后丢弃旧句」）
背压与降级引擎须提供队列水位；L1 依据水位触发降级为「仅原文」或暂停，不得无界缓冲（硬约束 C4）
隐私字段locality() 为 UI 必读：Remote 时开启前必须显式授权，本地模式必须可用

P-04PlayerCore — 播放能力

trait PlayerCore {          // 每个实例对应一路画面（多屏即多实例）
  fn load(&self, ref_: PlayableRef, start_at: Option<Progress>) -> Result<()>;
  fn command(&self, cmd: PlayerCmd);                    // play/pause/seek/rate/volume/track-select/subtitle-style
  fn events(&self) -> EventStream<PlayerEvent>;          // position/tracks-changed/eof/decoded-error/buffering
  fn audio_tap(&self, mode: TapMode) -> Option<AudioTap>;  // 供 SubtitleEngine 取 PCM；关闭时为 None（零开销）
  fn set_muted(&self, muted: bool);                      // 音频焦点：非发声窗口置静音仍继续解码
}
  • 多实例：每格一个 PlayerCore 实例，故障与状态互不影响（C3）；实例生命周期由 L1 的 PlaybackService 管理。
  • 预览实例：悬停预览复用同一个 PlayerCore，但与正式播放实例分两类：由 L1 单独创建、常驻 set_muted(true)、不注册音频焦点、不写进度仓库（PRD 共享规则「预览实例与进度隔离」）。
  • 音频焦点：「哪一路发声」是 L2 AudioFocus 策略的输出，通过 set_muted 下发，不在 UI 层直接操作音频设备（PRD 共享规则「音频焦点」）。
  • 字幕共性：外挂、内嵌、实时生成三类字幕最终都走同一字幕渲染通道，优先级由 L2 计算（PRD 共享规则「字幕轨道优先级」）。

P-05TagDimension 配置 — 标签维度

标签维度不是代码里的枚举，而是配置 + 数据驱动的定义，新增维度只需登记一条定义并声明其取值方式。

{ "id":"genre", "label":"内容类型", "selector":"multi", "source":"metadata",
  "expand":"value", "order":1, "editable":true, "lockable":true }
  • source 取值：metadata（来自 P-02）、derived（系统按事实归集，如时长/清晰度/字幕状态）、user（用户创建）。
  • derived 维度的取值规则以表达式或注册的派生器声明，使 FR-03「系统自动，不可手动编辑」可配置而无需改检索代码。
  • 检索组合逻辑（同维度 OR、跨维度 AND）实现一次，作用于全部维度，因此新增维度天然获得正确语义（硬约束 C6）。

05扫描入库链路

设计要点
  • 「条目先可用，元数据后补齐」是 PRD 失败恢复路径的技术实现方式：即使所有元数据源都不可用，海报墙与播放仍完整可用。
  • 派生维度（画质、时长区间、字幕状态）只在 probe 阶段计算一次并可缓存，避免每次筛选重算。
  • 去重键选择「源 + 规范化相对路径」，在线源用「规范化 URL」；稳定键不随元数据变化，否则先入库再补元数据会破坏幂等。

06实时字幕链路

机制规则对应 PRD
句界驱动输出以 VAD 静音切分为主、标点判定为辅输出 Final；Partial 仅用于超长句的视觉占位，不进入保存的轨道FR-05「按句为单位输出」
未保存结果保护关闭字幕时若会话内存在未保存的 Final，默认落库为字幕轨道并提示（可改为丢弃）FR-05 / 共享规则「不可逆动作」
保存产物保存即以 SubtitleTrack(source=generated) 落库并绑定条目，语种与时间轴一并持久化FR-05「已保存为轨道」
引擎切换Local/Remote 可并存且可在设置中切换默认；切换只改注册表配置，不改动 SubtitleServiceFR-07「字幕能力可替换」
崩溃恢复ASR 子进程异常退出时上报 Failed 并给出三个出口；播放与 UI 不受影响，可原地重启子进程硬约束 C4

07多屏播放链路

关键结论 「多视频同时播放」在技术上等于多实例 + 集中治理，而不是一个能播多路的特殊播放器。这样单格故障、进度持久化、实时字幕归属都自然成立，且将来把布局从 4 路扩到 6 路只是治理参数变化（FR-07 的增量演进要求）。

预览实例与解码额度（悬停自动播放）

悬停预览不引入第二条解码链路：它复用 PlayerCore，但作为一类低优先级实例挂在同一处资源治理之下，对应 PRD 共享规则「预览实例与进度隔离」。

维度设计理由
实例归属由 L1 PlaybackService 创建并持有，同一时刻最多 1 路PRD 规定单路并发；集中持有才能统一限流与释放
音频创建即 set_muted(true)，不注册 AudioFocus，audio_tap 恒为 None预览不得抢占发声窗口，也不需要字幕识别
额度共享预览与多屏共用同一份并发解码额度；额度不足时预览被拒绝并回传原因避免「预览 + 4 路多屏」同时解码导致丢帧
进度隔离预览实例不绑定「播放会话」，不进入进度写入路径浏览行为不产生持久化状态，避免脏进度
抢占顺序过载时先终止预览，再考虑降低多屏画质；不擅自关闭用户已开的窗口预览是价值最低的负载，牺牲它的体验损失最小
生命周期鼠标移开 / 片段播完 / 切换海报即释放，空闲不常驻避免长期占用解码器与显存
失败的可见性 预览被拒绝不是静默失败：L1 返回拒绝原因，L0 在海报浮层标注（已关闭 / 无可用片段 / 多屏额度不足），与 PRD FR-02「精华片段预览规则（悬停自动播放）」的三种降级态一一对应。

08数据模型与迁移

表结构面向硬约束 C6（增量演进）：对「维度与取值」做通用建模，新增标签维度或新来源不需要改表。

迁移规则做法对应约束
前进式迁移只允许 vN → vN+1 的脚本化迁移，禁止依赖降级；应用启动时检查版本，低版本数据文件一律引导升级而非静默改写C5
迁移前备份执行迁移前自动复制数据库文件为带版本后缀的备份，保留最近 2 份；迁移失败则回滚并提示C5
双读兼容期字段重命名/拆表时，先新增列并回填，再在新版本中停止写入旧列；旧列在下一个大版本才删除C6
导出/导入导出包为「结构化 JSON + 海报与生成字幕资源」，导入按稳定键合并并保留用户字段；导入时同一 stable_key 冲突以用户数据为准FR-07「数据可迁移」
派生数据可重建派生标签、FTS 索引、海报缓存均可在不丢用户数据的前提下重建，因此允许在必要时清空重算C5 / C6

09迭代与兼容策略

功能开关

  • 每个新功能在 setting 中有默认关闭的开关（实时字幕、多屏混合输出、云端引擎、定时重扫）。
  • 开关关闭时对应 UI 入口隐藏、后台任务不启动，代码路径仍可被测试覆盖。
  • 开关两级：default_off（内部尝鲜）与 default_on（默认可用），灰度通过更新通道实现，不引入远端配置依赖（C1）。

模块独立升级

  • 升级不触发重新入库：入库与元数据是幂等过程，升级后仅补增量与缺失字段。
  • 替换 ASR 引擎或播放内核不改变数据模型，因此不需要数据迁移。
  • 新增标签维度只需 tag_dimension 增一行并回填派生值，检索交互不动。

测试布局

  • L2 领域单测：检索组合语义、续播规则、轨道优先级、音频焦点移交 —— 这些是回归风险最高的规则，不依赖 IO。
  • L3 契约测试：每个端口写一套可复用测试，任何新实现（新源类型/新元数据源/新引擎）必须通过，保证可替换性不被破坏（C2）。
  • 端到端：覆盖「添加源 → 入库 → 筛选 → 悬停预览 → 播放 → 开启字幕 → 保存轨道 → 多屏推入」主旅程。
  • 预览回归：悬停 300ms 才启动、单路并发（切海报先终止上一路）、静音且不改音频焦点、不写进度、多屏额度不足时被拒绝并回传原因 —— 这些是 PRD 共享规则「预览实例与进度隔离」的验收点。
  • 迁移测试：以历史版本数据库样本验证迁移脚本，确保升级不丢用户数据。

已知风险与应对

  • R1 多路硬解共存：GPU 同时解码 4 路 4K 可能超限。应对：上限自适应探测 + 过载上报降级提示；若不可达则回退 Electron 方案（见第 2 节备选）。
  • R2 本地 ASR 延迟：CPU 模式可能达数秒。应对：默认推荐可用 GPU/加速后端，UI 明确展示延迟与占用；云端作为可选开关（P-03 已支持）。
  • R3 元数据源可用性：单一来源失效。应对：多提供者并存 + 失败降级为「元数据待补全」，不阻塞入库。
  • R4 迁移失败导致数据损坏：应对：迁移前自动备份 + 失败回滚 + 导出包兜底。

关键约束（为什么格内字幕层要固定高度）

mpv 原生子窗口按物理像素精确覆盖 .screen-area 且恒在网页之上（z-index 无效），因此格内字幕 不能画在画面区上，只能画在画面区之外：.cell-top（格头）/ .cell-sub（字幕层，本次新增）/ .cell-bar（格内控制条）都不被原生窗口覆盖。.cell-sub 取固定高度而非自适应， 是为了避免「字幕出现 / 消失改变画面区高度」→ 原生窗口与格位错位。

  1. 构建失败＝环境未配齐，而非代码问题：直接 cargo build / cargo check 报 error calling dlltool 'dlltool.exe': program not found 或 ld: cannot find ...\rustlib\...rlib。原因是 A.1 / A.13 的构建配方必须整条执行： MinGW（%TEMP%\mingw-m0\mingw64\bin）进 PATH 提供 dlltool、 AR 与 CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER 指向 rust-lld、 CARGO_TARGET_DIR 与 TEMP/TMP 落纯 ASCII 路径（本轮沿用 X:\target / X:\tmp）。 少任意一项都会以「找不到工具」的形式报错，容易被误判为代码缺陷。
  2. 编译器拦下一处上下文归属缺陷（E0308）：subtitle_start 里 let (slot, audio) = audio_for(&state, slot)?; 把「兜底后的实际屏位」绑回了外层 slot: Option<u32>，导致随后的 match slot 无法区分 「有 slot ＝ 格上下文 / 无 slot ＝ 主上下文」。修正为独立绑定 let (_tap_slot, audio) = ...，上下文归属不再被兜底值覆盖。
  3. 并行测试在受限沙箱下会挂起：同时设 CINEMA_LIBMPV（真实解码）并默认并行时， cinema-adapters 契约用例长时间不返回；改为 --test-threads=1 且不设 CINEMA_LIBMPV 后 27 项 1.98 s 全绿。 属沙箱环境限制，非代码问题（记此以备后续复现）。

范围决策（方案 A 的三个前提）

  1. 解析引擎用 yt-dlp 子进程，不内置通用抓取器：站点结构变化频繁， 泛型抓取器难以维护；yt-dlp 由外部维护且自带请求头 / 指纹伪装等对抗逻辑 （目标站点走 Cloudflare，实测需 --impersonate chrome 才不被 403）。 项目不引入 HTTP / TLS 依赖，只在 L3 新增一个「进程运行器」端口与实现。
  2. 新增源类型＝新增实现＋注册（不改 L2 核心流程）：L2 只新增 SourceKind::OnlineSite 枚举值与 DiscoveredItem.poster_ref 字段， discover / open / probe 三段流程与 ImportService 原样复用 （仅在线源在导入期跳过逐条探测，见下）。
  3. 封面「缓存到本机海报目录」而非每次联机取：复用既有约定 <数据目录>/posters 与 media_item.poster_id （其值即该目录下的文件名），因此本轮不需要数据库迁移； 封面按按需懒抓：文件已存在则直接复用， 「是否已有封面」在文件层面一律按「文件是否存在」判定，重复导入不会重复下载。

A.19 人工确认项（联网导入）

在正常桌面会话（非受限沙箱）中启动后核对下列 7 点（A.3 / A.5 / A.7 / A.9 / A.11 / A.13 / A.15 / A.17 的项目仍适用）：

  2. 列表页枚举：粘贴目标列表页（如 https://hanime1.me/search?genre=%E8%A3%8F%E7%95%AA）后点「开始导入」， 回执应给出「发现 N 条，入库 M 条」，海报墙随即出现条目，源清单出现一行以主机名命名的源。 该站无 yt-dlp extractor，发现会先失败一次再回落 HTML 解析，单条 URL 的耗时明显长于本地源， 属预期。
  3. 在线播放：原方案 A 口径为「打开时用 yt-dlp 实时解析直链并把 http_headers 交给 mpv」。该口径已被实测否定并改为方案 B（边下边播）——目标站点走 Cloudflare， mpv（libcurl）直连其 CDN 一律 [curl] error: SSL connect error。 现行口径与确认清单见 A.20。
  4. 封面是卡片封面 art，不是视频帧：条目卡片应显示站点列表页卡片上的封面图， 且随浏览逐张出现（导入后由后台任务按整页顺序下载；取值口径见 A.21）。 封面文件应出现在 <数据目录>/posters/online-<hash>.jpg （数据目录默认 %LOCALAPPDATA%\Cinema，可用 CINEMA_DATA_DIR 覆盖）。
  5. 重复导入幂等：同一 URL 再导入一次，条目数不应翻倍（稳定键合并）， 且不应重复下载封面（已落盘的文件直接复用）。
  6. 失败降级不阻塞：单个 URL 失败只提示该条、其余条目照常入库；封面抓取失败的条目 仍能入库并播放，卡片回落占位图（不应破图）。
  7. 无残留子进程：导入 / 滚动封面结束后，任务管理器中不应留下 yt-dlp.exe 子进程（超时 120s 强杀逻辑仍在）。

  1. 依赖外部 yt-dlp：引擎不在仓库内、不随包分发，需用户自行放置 / 更新；缺失时联网导入不可用（不影响其余功能）。
  2. 目标站点无 extractor，列表页靠自行解析 HTML：发现环节依赖站点页面结构（同源、含图片的卡片链接）， 站点改版即可能失效；对 yt-dlp 有 extractor 的站点会直接走结构化路径，不受此影响。
  3. 封面后台整页抓取、逐张渐进出现：后台每张封面一次子进程（实测数秒/张）， 大列表首次浏览会持续数十秒至数分钟；抓取失败的条目回落占位图，不影响播放（见 A.21）。
  4. 时长按需解析：在线源在导入期不逐条探测，时长在首次播放时解析；因此首次导入后条目暂无时长 （无「继续观看」百分比与悬停预览，属预期）。
  5. 在线条目无悬停预览：悬停预览仍只对本地文件生效；本轮已在 L0 显式拒绝（返回 「在线条目暂不提供悬停预览」），避免悬停一次就触发整部影片的下载（见 A.20）。
  6. 无「默认关闭」开关：本条不设全局开关——入口本身要求用户显式粘贴 URL 才会联网， 属「显式开启即等价」；其余新增功能仍遵循 C6 默认关闭。
  7. 未做的范围：不做站点登录 / Cookie 导入、不做列表分页翻页、不做封面手工替换。 （「不做下载到本地」已被 A.20 的边下边播取代。）

A.20 「联网在线播放：边下边播（方案 B）」实施与验证记录

本条承接 A.18，取代其中「打开时用 yt-dlp 实时解析直链并把 http_headers 交给 mpv」 的播放口径。触发是用户反馈的两个现象：「联网导入失败」与 「点击了播放软件卡住，后面恢复后也无明确响应，下面多了个进度条，但是没有进视频播放界面」。 实施口径由用户当场确认：按方案 B 执行，并修复卡死问题。 A.18 的发现（列表页枚举）与封面缓存部分不受影响，本轮只重做播放路径与 阻塞点。

记录日期 2026-10-19 对应阶段 联网导入（M7 前置） · 非 §10 验收依据 附录 A.20（非 §10） 取代 A.18 的 open / probe 口径

两条独立根因（均有硬证据）

  1. 卡死 = 同步命令在主线程上跑阻塞子进程。Tauri 的同步命令（无 #[tauri::command(async)]） 直接在主线程执行——该结论已在框架源码中核实 （tauri-2.12.4\src\manager\mod.rs 的命令派发与 src\ipc\command.rs 的 同步分支）。旧实现里 open 要串两次 yt-dlp（抓封面 + 解析直链，实测合计约 10 秒）， item_cover 每张封面再阻塞最多 5 秒，命令体一阻塞，整个 webview（含渲染）随之冻结。 这也解释了「恢复后无明确响应」——用户看到的是命令终于返回、但没有任何可播内容。
  2. 无画面 = mpv 被站点反爬拦下，且失败被静默吞掉。直接把 yt-dlp 解析出的 mp4 直链交给 mpv 时， mpv 内部 libcurl 一律报 [curl] error: SSL connect error 并 loading failed (reason 4)：目标站点走 Cloudflare，其 CDN 对非浏览器指纹的连接直接拒绝， 而 yt-dlp 自带的 curl_cffi 指纹伪装（--impersonate chrome）能过。 此外 apply_common_options 里设了 msg-level=all=no，把 mpv 日志全部关掉， 失败因此完全不可见，表现为「进度条在、画面不来、也没有任何提示」。

方案 B 口径（本轮确立）

  1. 不再把直链交给播放内核，改为「边下边播」：yt-dlp 后台把影片写到 <数据目录>/streams/online-<hash>.mp4，mpv 打开这个正在增长的本地文件。 可行性已实测：该站 mp4 的 moov 在文件头，下载到 134MB（约 14 秒）时 mpv 已能读出完整时长 duration=910.016s，即可边下边看。
  2. open 必须立刻返回（毫秒级）：只做「算缓存文件路径 + 起一个分离下载」， 不做任何等待；probe 直接返回 StreamFacts::default()，零联网、零子进程； PlayableRef.headers 恒为空（读本地文件不需要请求头）。
  3. 不做「就绪阈值」判定，交给心跳自纠正：文件还没长成时播放内核首次 loadfile 会失败， 由组合根在既有 400ms 心跳（poll_screens）里对在线格做一次节流补发 loadfile（空闲 1.5s 以上才补），失败即自愈，不需要精确预测「何时可播」。
  4. 「下载前沿 EOF」不是「看完」：边下边播时 mpv 播到已下载尽头会报 EOF， 因此 ended 需门控（at_end() && downloads.state != Running）； 仅当文件字节数较上次增长时才往回 seek 500ms 续看，避免同一段结尾反复重播。
  5. 失败必须可见：下载失败且文件为空时上抛故障文案，经心跳的 fault 字段 由前端提示一次（去重），修掉 A.18 遗留的「无明确响应」。
  6. 子进程三处收尾：关闭单格（close_slot）、关闭全部多屏（close_all_screens 调 stop_all 兜底）、程序退出（RunEvent::Exit）都要终止 yt-dlp，防孤儿进程。
  7. 封面改为后台线程抓：item_cover 不再在命令体里等 yt-dlp， 而是登记一次在途任务后立刻返回空串，前端有限次重试取回。 取证口径与去重粒度已在 A.21 修正（改为按「源」抓列表页卡片封面， 在途登记保留 300s 而非抓完即删）。 在线条目一律拒绝悬停预览（否则悬停一次就会触发整部影片的下载）。

A.21 「联网封面来源修正：改用列表页卡片封面」实施与验证记录

本条承接 A.18 / A.20，取代其中「封面由详情页 --write-thumbnail 抓取」的取值口径。 触发是用户实测反馈：「发现没有下载封面图，用的看着像是视频截图」。 发现（列表页枚举）与播放（边下边播）路径不变，本轮只改封面「取哪张图」与「怎么取」。

记录日期 2026-10-19 对应阶段 联网导入（M7 前置） · 非 §10 验收依据 附录 A.21（非 §10） 取代 A.18 / A.20 的封面取值口径

根因（有硬证据）

  1. 取错了图：详情页 og:image 是视频帧，不是封面 art。旧 ensure_cover() 对详情页跑 --write-thumbnail --convert-thumbnails jpg，yt-dlp 取到的是详情页的 og:image——一张 1024×576（16:9）的视频截图。目标站无 yt-dlp extractor， 详情页由 generic extractor 处理，而 generic 只认 og:image。
  2. 站点真正的封面 art 在列表页卡片上，且旧代码把它丢掉了。真实列表页的一手证据 （--write-pages 落盘的 HTML）显示每张卡片的图是 https://vdownload.hembed.com/image/cover/<id>.jpg?secure=<token>,<expiry>， 与条目一一对应（该页 41 个 /image/cover/ 引用对应 41 条条目；另 13 个 /image/icon/ 是站点图标；poster= / data-src= / background-image 均为 0 个）。但 parse_cards() 当时只用 inner.contains("<img") 判「有没有图」，从不读取 src。
  3. 视觉上「像截图」还叠加了裁切：前端卡片是 aspect-ratio: 2 / 3 竖版 + object-fit: cover，16:9 的帧被硬裁成 2:3——用户看到的正是被裁过的视频画面。 同页广告位的示例图是 268×394（≈2:3 竖版），与卡片槽位一致，也印证「卡片该放竖版 art」。
  4. 机制可行性已实测：yt-dlp 的 generic extractor 能直接下载任意图片直链 （[generic] jpeg: Downloading 1 format(s): 0），且 -o "<dir>/name.jpg" 会精确产出 name.jpg（用 httpbin 的 JPEG 验证文件头为 FF D8 FF）。
旧构建产物的证据

缓存目录 %LOCALAPPDATA%\Cinema\posters 下的 41 张 online-*.jpg 经逐个读取尺寸，全部为 1024×576（16:9 视频帧尺寸），与站点卡片图的 /image/cover/ 路径不一致——即「下载下来的根本不是封面」。本轮已把这 41 张派生缓存全部清理， 以强制走新的取值路径。

修正口径（本轮确立）

  1. 封面取列表页卡片锚点内第一张 <img> 的 src：绝对化时 不施加「同站」过滤（封面常放在独立 CDN 上，是异站直链）。ListingCard 新增 cover: Option<String>，结构化枚举路径（路径一）该字段为 None。
  2. 直链图片同样借 yt-dlp 的指纹伪装下载：--impersonate chrome --no-playlist --force-overwrites -o <海报目录>/online-<hash>.jpg <封面直链>； 不把非零退出当失败（文件常已落盘），以文件内容为准。
  3. 落盘后校验 JPEG 文件头（FF D8 FF）：不是 JPEG 就删除——令牌过期 / 被挡时 CDN 可能返回 HTML / JSON 错误页，那种「文件」贴到卡片上就是破图。
  4. 按「源」而非按条目去重：一次列表页抓取即含该页所有卡片封面，因此第一张缺失时 触发一次即可；在途登记（AppState.covers_inflight）保留 300s、 抓完不删，以避免「本来就没有封面的条目」被重试时把列表页反复抓一遍。 这同时是重启后的自愈路径（封面文件被清掉 / 换机导入后，一打开库即触发补抓）。
  5. item_cover 只读本地文件、绝不联网：命中即返回 data URL，未命中返回空串 并顺手挂起一次后台抓取（同步命令跑主线程，任何等待都会冻结界面）。
  6. 前端改为每张卡片各自独立重试（去掉原来的串行队列 coverChain，最多 20 次 × 2s）： 后端已只读文件、请求廉价，可并发轮询，不再需要「一次只请求一张」来限制子进程数 （子进程数由「按源去重」保证）。

已知限制
  1. 封面文件是派生缓存，不随库导出：换机导入或手工清空 posters 后， 封面会在下次打开库时由后台按源补抓（自愈），期间逐张出现。
  2. 封面结构依赖站点页面：若站点改版使卡片图不再位于条目锚点内（或改为 data-src / 背景图），则抓不到封面而回落占位图；本轮只认锚点内第一张 <img> 的 src。
  3. 卡片裁切仍在：卡片槽位为 2:3 竖版 + object-fit: cover， 若站点封面本身是横版，仍会按槽位裁切（但显示的是封面 art，不再像视频截图）。
  4. 一次只抓当前页：沿用 A.18 限制——不做分页翻页，故只抓当页条目的封面。
  5. 在途登记 300s 内不重复抓：若某次抓取整体失败（如临时断网）， 该源在 300s 内的后续重试不会重新抓取；超时后自然放行。
